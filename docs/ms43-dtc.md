# Чтение и очистка DTC MS43

Реализовано в `dmelab-ms43::Session::read_dtcs()`, CLI `dtc` и UniFFI
`Ms43Client.readDtcs(timeoutMs)`. Это чтение собственной памяти ошибок MS43;
очистка доступна через `Session::clear_dtcs()`, CLI `clear-dtc` и UniFFI
`Ms43Client.clearDtcs(timeoutMs)`. Эти операции не разблокируют flash и не меняют прошивку.

## Использование

```sh
cargo run -p dmelab-cli -- dtc
./target/release/dmelab dtc --port /dev/cu.usbserial-FT1234 --timeout-ms 2000
# Очистить память ошибок:
./target/release/dmelab clear-dtc --timeout-ms 2000
```

Работает обычный автоматический выбор единственного `usbserial`-порта.
CLI и FFI начинают на 9600 8E1 и идентифицируют MS43 перед чтением.
Rust API идентифицирует свежую сессию автоматически; уже идентифицированная
сессия использует текущую согласованную скорость. Само чтение DTC скорость не меняет.
`--timeout-ms` ограничивает каждую транзакцию, включая echo и ответ, а не всю операцию.

Возвращается `Vec<Dtc>` с полями:

| Поле | Значение |
| --- | --- |
| `code: u8` | Собственный однобайтовый код MS43 |
| `frequency: u8` | Частота из байта 2 записи |
| `data: [u8; 4]` | Байты 4–7 без интерпретации |
| `raw: [u8; 10]` | Полная исходная запись |

В Kotlin массивы представлены `ByteArray`, код и частота — `UByte`.
CLI выводит код десятичным и hex-числом, частоту, data и raw.
Текстовая расшифровка, перевод в Pxxxx и определение active/stored отсутствуют:
исследованные исходники не устанавливают такую семантику.

## Обмен и полнота

Запрос — payload `04 SS`, где `SS` — индекс первой записи: 1, 11, 21…
Первый полный пакет — `12 05 04 01 12`. Общий протокол проверяет echo,
адрес `12`, длину, XOR и статус `A0`. Ответ содержит общее количество в байте 3,
затем записи по 10 байт с байта 4. Дубликаты кода сохраняют первую запись.

Наш контракт строже исходного reader MS4x Flasher:

- Каждая страница должна содержать ровно `min(10, оставшееся количество)` записей;
  неполная запись или пропущенная часть страницы возвращает ошибку.
- Общее количество должно оставаться постоянным. При изменении нужно повторить
  чтение целиком. Это не атомарный снимок: изменение записей без изменения числа
  ошибок протоколом обнаружить нельзя.
- Таймаут, несовпадение echo и ошибки framing/XOR допускают четыре попытки
  конкретной страницы с паузой 200 мс и очисткой буферов перед новым запросом.
  Отрицательный статус, ошибка настройки/отключение транспорта и нарушение
  полноты завершают операцию сразу.
- Индекс вычисляется в `u16`: последний запрос 251 при количестве до 255
  завершается без переполнения или возврата к индексу 5.

При сбое возвращается `Error::DtcRead { start_index, source }`, в Kotlin —
`DmeException.DtcRead` с `startIndex` и `details`. Частичный список не выдаётся как
успех. CLI печатает `No DTCs found.` только после успешно проверенного пустого ответа.
Число уникальных кодов может быть меньше объявленного количества из-за дубликатов.

## Очистка памяти ошибок

Команда без аргументов — payload `05`, полный пакет `12 04 05 13`.
Она подтверждена одновременно в MS4x Flasher (`communication 0x06000013`) и
`FS_LOESCHEN` из `~/git/kek/deepobd/analysis/ms43/source/MS430DS0.b1v`.

```rust
session.clear_dtcs()?;
```

```kotlin
client.clearDtcs(timeoutMs = 2000u)
```

Свежая сессия сначала идентифицирует MS43. CLI и FFI начинают на 9600;
уже идентифицированная Rust-сессия сохраняет текущую скорость. Выполняется
одна команда очистки с обычным бюджетом транзакции, проверками echo,
адреса, длины, XOR и статуса `A0`. Разгон, команды стирания flash, отдельный
сброс адаптаций и выборочное удаление отдельных кодов не выполняются.

`Ok(())` / Kotlin `Unit` означает получение подтверждения ECU. Это не обещание
пустой памяти после операции: постоянная неисправность может появиться снова.
CLI сообщает именно подтверждение очистки. Для проверки текущего состояния
вызовите `read_dtcs()` / `readDtcs()` или команду `dtc` отдельно.

Автоматических повторов нет. При потере ответа ECU мог уже выполнить очистку;
повторять изменяющую состояние команду незаметно для вызывающей стороны нельзя.
Отказ или отсутствие подтверждения возвращается как `Error::DtcClear { source }`,
в Kotlin — `DmeException.DtcClear` с `details`. Ошибка идентификации до отправки
очистки возвращается в своём исходном виде. Состояние реального ECU при ошибке
обмена не считается известным.

## Основания и проверки

Источник — `~/git/kek/ms4x/MS43_DTC.md`, `tools/ms43_dtc.py` и листинги
`analysis/ms43/ms43-dtc-{protocol,record}.il.txt`: reader `0x06000019`, wrapper
MS43 `0x060000db`, constructor записи `0x06000129`. Пауза 200 мс передаётся из
UI-поля `0x04000148` в поле `A.B::C`. Исправлены найденные в исходном reader
молчаливый возврат partial после сбоя второй страницы и переполнение byte-индекса.

Две основные автономные проверки покрывают повтор конкретной страницы,
переход до 255, first-wins и декодирование полей, а также отказ вместо partial,
неполную запись и корректный пустой ответ. Это необходимое исключение из фриза
на тесты. Работа с реальным FTDI/ECU и фактический адрес ответа пока не подтверждены.
Новый API также проверен через сгенерированный Kotlin на macOS: автоматическая
идентификация, пагинация, повтор и ошибка второй страницы проходят через реальную
UniFFI-границу с подготовленными ответами транспорта Kotlin.

Для очистки добавлена одна основная проверка точного пакета, подтверждения `A0`,
отказа `B0` и отсутствия повторов после потери ответа. Это необходимая проверка
изменяющей состояние операции в рамках исключения из фриза на тесты.
Через Kotlin → UniFFI → Rust с подготовленными ответами проверены идентификация,
подтверждение очистки, отказ ECU, потеря ответа без повторов и запрет отправки
очистки неподдерживаемому ECU. Android Kotlin скомпилирован; `.so` для обоих ABI
пересобраны. Очистка памяти настоящего ECU не выполнялась.
