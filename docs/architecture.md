# Архитектура dmelab

## Назначение

dmelab предоставляет общее Rust-ядро для диагностики DME и работы с прошивками. Первой реализуем связку MS43 и FTDI K-line. Клиенты — CLI и UI для macOS, затем Android. Архитектура предусматривает дополнительные DME, включая MS42 и MS41, и транспорт через ESP32 с собственной прошивкой.

Диагностические цели: чтение ошибок и текущих параметров по образцу DeepOBD. Цели программирования: чтение и запись прошивок по образцу MS4x Flasher. Это ориентиры функциональности; совместимость с каждым блоком и набор операций подтверждаются отдельно.

## Границы записи прошивки

Перепрошивка bootloader не входит в функциональность проекта. Не реализуем его стирание, запись или восстановление, включая отдельные команды и обходные режимы CLI/API. Для MS43 ориентируемся на поведение записи разобранного MS4x Flasher 1.6.0, описанное в `~/git/kek/ms4x/MS43.md`.

| Операция MS43 | Входной образ | Изменяемые секции ECU |
| --- | --- | --- |
| Full Write | 512 KiB | Program и calibration |
| Partial Write | 64 KiB или 512 KiB | Только calibration |

Название Full Write означает запись program и calibration из полного образа. Наличие bootloader в файле размером 512 KiB не разрешает передавать его на запись. Область bootloader и пропуск в образе не включаем в команды стирания и записи.

В Full Write источник program начинается со смещения файла `0x10000`, адрес ECU — `0x090000`, передаётся до `0x5FFF0` байт. Источник calibration начинается со смещения `0x70000`, адрес ECU — `0x070000`, передаётся до `0xFFEF` байт. В Partial Write источник calibration начинается с `0` для образа 64 KiB либо с `0x70000` для образа 512 KiB. Сохраняем последовательность разблокировки, подготовки, стирания, передачи и финализации из исследования; не заменяем её линейной записью всего файла.

Чтение bootloader в составе Full Read допускается. Пересчёт контрольных сумм входного образа сам по себе не расширяет разрешённые секции записи. Для последующих DME правило исключения bootloader сохраняется, а адреса и процедуры определяются отдельно.

Минимальные необходимые тесты записи должны проверять допустимые адреса и длины и отсутствие команд стирания и записи bootloader; это исключение из фриза на новые тесты. Аналогия с MS4x Flasher задаёт целевое поведение; аппаратную работоспособность подтверждаем отдельно.

Полное/частичное чтение и запись реализованы в `dmelab-ms43::Session`; CLI предоставляет команды `read` и `write`. Каждая операция идентифицирует MS43 на 9600, выполняет предварительные проверки, согласует повышенную скорость и после передачи пытается вернуть 9600. Разметка образов, проверки и ограничения описаны в [документе flash](ms43-flash.md).

## Слои и зависимости

```text
CLI на Rust ───────────────────┐
macOS UI / Android → UniFFI ───┤
                              ↓
                Общий API и возможности DME
                              ↓
                Реализация MS43 / MS42 / MS41
                              ↓
                Протокол и управление сессией
                              ↓
                Контракт транспорта
                              ↓
                FTDI K-line / ESP32 / другие
```

Ядро не зависит от UI, путей последовательных устройств, Android USB API или диалогов разрешений. Особенности блока остаются в реализации DME; особенности подключения — в транспорте. Общие части протоколов выделяем по мере подтверждённого повторного использования.

При реализации слоёв следуем [правилам Rust](rust-guidelines.md): простота кода важнее оптимизаций, а дополнительные абстракции требуют конкретного обоснования.

## Планируемая структура

| Каталог | Ответственность |
| --- | --- |
| `crates/dmelab-core` | Общий API, контракты DME и транспорта, возможности, ошибки, прогресс и управление операциями |
| `crates/dmelab-ms43` | Протокол и сессии MS43, диагностика, разметка прошивок, контрольные суммы, чтение и запись |
| `crates/dmelab-transport-serial` | Кроссплатформенный serial-транспорт на `serialport`; первая аппаратная проверка на macOS с FTDI K-line |
| `crates/dmelab-cli` | Команды, файлы и вывод результатов; прямые вызовы Rust API |
| `crates/dmelab-ffi` | Адаптер публичного API для UniFFI и конфигурация генерации bindings |
| `apps/` | Будущие приложения macOS и Android |
| `docs/` | Архитектура, описание протоколов и результаты проверок |

Позднее добавляем `dmelab-ms42`, `dmelab-ms41` и `dmelab-transport-esp32`. Каталоги создаём вместе с реализацией; таблица задаёт целевую структуру.

## Расширение по DME

Каждая реализация блока предоставляет общий API и явно объявляет поддерживаемые возможности: идентификацию, чтение ошибок, текущие параметры, чтение калибровок, полное чтение и виды записи. Клиенты получают эти возможности от библиотеки и отображают доступные операции. Неподдерживаемая операция возвращает структурированную ошибку.

Специфичные параметры и форматы данных представляем явно, без предположения об одинаковых датчиках, единицах измерения или областях памяти у всех DME. Последовательности программирования, контрольные суммы, адресация и особенности сессий принадлежат реализации блока.

Добавление MS42 или MS41 требует исследования и реализации соответствующего протокола. Совпадение транспорта K-line само по себе не означает совместимость команд или формата прошивки.

## Расширение по транспорту

Контракт транспорта покрывает чтение и запись буферов, настройку линии, таймауты и закрытие соединения. Транспорт сообщает свои возможности и ограничения; неподдерживаемые параметры отклоняются явно.

Для MS43 реализована [согласованная смена скорости](ms43-baud-rate.md): реализация DME отправляет запрос и проверяет подтверждение, выдерживает 200 мс, затем вызывает настройку UART у транспорта. CLI начинает на 9600 и возвращает эту скорость перед выходом. Неоднозначный результат переключения блокирует дальнейшие команды сессии.

Обработка пакетов, echo, ответов и повторов принадлежит протокольному слою. Приём учитывает частичные чтения и несколько пакетов в одном буфере. Одной сессией управляет один последовательный исполнитель.

Непрерывный live-опрос MS43 реализован в Rust как один блокирующий вызов
`Session::stream_live_data` на 9600: идентификация один раз, межзапросные паузы,
восстановление после пакетных ошибок и отдельные события замеров/восстановления.
CLI и UniFFI используют этот цикл. FFI держит Rust-сессию локально на время
вызова; отдельный stop-control содержит только атомарный флаг и не требует
занятого клиентского mutex. Создание потока остаётся ответственностью приложения.
Однократный API сохранён. Подробности — [live data](ms43-live-data.md).

Клиент может выбрать любую непустую комбинацию пяти live-блоков через
`LiveDataSelection`. Выбор и результат `SelectedLiveData` типизированы в
`dmelab-ms43`; CLI и UniFFI передают выбор без собственных DS2-команд.
Непрочитанные группы отсутствуют явно. Общий Rust-цикл восстановления опрашивает
только выбранные блоки; прежний API полного `LiveData` использует тот же цикл
с выбором всех трёх. Набор фиксирован на один вызов stream.

Дополнительные `0B 92` и `2B 05` выбираются явно; прежние три блока остаются
набором по умолчанию. Неравномерность и пропуски возвращаются с номерами
цилиндров и исходным статусом системной проверки, без автоматического запуска.
DISA, вентилятор и завершение диагностического управления — отдельные
синхронные операции реализации MS43. Команды воздействия не повторяются
автоматически и не входят в live-цикл. Транспорт и FFI не хранят копии логики
управления. [Контракт исполнительных тестов](ms43-actuators.md).

Для ESP32 способ связи с приложением пока открыт. При беспроводном соединении чувствительные к задержкам действия выполняются рядом с K-line на ESP32. Поэтому будущий контракт может включать выполнение локальных последовательностей обмена; его окончательную форму определяем прототипом. Полная прозрачность сетевого канала для UART заранее не предполагается.

## Модель выполнения

Библиотека и CLI используют синхронный блокирующий API без Tokio и других async runtimes. Rust-код проекта, включая будущую FFI-обёртку, не создаёт потоки и фоновые исполнители. CLI выполняет операции в основном потоке; управление одной сессией последовательно. Подробности зависимостей: [стек Rust](rust-stack.md).

Прогресс передаём синхронными обратными вызовами, ожидание ввода ограничиваем таймаутами. Отмена кооперативная и зависит от этапа протокола.

## UniFFI и приложения

Генерацией Swift/Kotlin bindings владеет библиотека dmelab. `dmelab-core` и реализации DME остаются обычными Rust-библиотеками; зависимость от UniFFI сосредоточена в `dmelab-ffi`.

FFI предоставляет `Ms43Client`, параметры операций, результаты, структурированные ошибки и прогресс. Реализованы идентификация, чтение/очистка DTC и чтение текущих параметров, чтение и запись flash. Непрерывный `streamLiveData` поддерживает кооперативную остановку через `LiveDataStreamControl.stop()`; отмена однократных и flash-операций пока не реализована. Очистка DTC отправляется однократно, без автоматических повторов, и требует подтверждения ECU; [контракт DTC](ms43-dtc.md). `read_live_data` объединяет три последовательных блока в типизированный результат, включая положения VANOS и команду DISA; [контракт текущих параметров](ms43-live-data.md). Приложение вызывает блокирующий API вне UI-потока и само управляет контекстом выполнения; библиотека потоки не создаёт. Будущая отмена flash определяется этапом операции: запрос отмены во время записи не должен безусловно разрывать соединение.

В FFI `Arc` и `Mutex` нужны для безопасного объекта UniFFI: приложение может вызывать его из разных потоков. `try_lock` отклоняет параллельный и повторный вход через `Busy`, не ставит операции в очередь. Протокольная сессия создаётся локально внутри вызова, требования `Send` к контракту ядра не добавляются. Неопределённая или невосстановленная скорость сохраняет состояние `NeedsReconnect` между вызовами.

Сборка библиотеки генерирует bindings и собирает нативные артефакты для целевых платформ. Приложение подключает соответствующий пакет; CLI вызывает Rust API напрямую, без FFI. Сначала допускается общая сборка в одном репозитории. Затем планируется выпуск версионированных пакетов, где bindings и нативная библиотека поставляются вместе в совместимых версиях.

Платформенный транспорт может принадлежать приложению. Для Android доступ к FTDI через USB Host остаётся на стороне Kotlin/Java: приложение управляет разрешениями и соединением, затем передаёт `KlineTransport` через интерфейс обратных вызовов. Мост реализован; конкретный Android USB-драйвер ещё не подключён. Контракт задаёт библиотека, обмен идёт буферами. Kotlin и `.so` собираются без Gradle; пакет — `dev.coldcat.dmelab.ffi`. [Сборка и контракт Android bindings](android-bindings.md).

Desktop feature `dmelab-ffi/desktop` добавляет `listSerialPorts` и именованный
конструктор `Ms43Client.openSerial`. Клиент владеет нативным портом через
`dmelab-transport-serial`; один OS handle сохраняется между операциями.
Транспорт выбирается внутренним enum: callbacks приложения либо native serial.
Оба используют общий mutex состояния клиента, правила `Busy`/`NeedsReconnect`
и локальную протокольную Session. Native serial передаёт исходные IO-ошибки
в протокол напрямую. `Arc<Mutex<SerialTransport>>` нужен для владения объектом
UniFFI и не создаёт потоков; общий Transport не получает ограничения `Send`.
Bindings генерируются отдельно для JVM desktop и Android с одинаковым пакетом,
а JNA и нативные ресурсы подключаются платформенными source sets.
Первая desktop-цель — macOS ARM. [Контракт desktop bindings](desktop-bindings.md).

## Порядок реализации и проверки

1. Перенести автономные алгоритмы MS43 в Rust, сохранив тестовые векторы и сравнение с исследовательскими Python-реализациями.
2. Добавить serial-транспорт и macOS CLI; проверить подключение и идентификацию на оборудовании.
3. Исследовать и реализовать чтение ошибок и текущих параметров, чтение калибровок и полное чтение прошивки.
4. Реализовать запись и проверить её на стенде, включая прерывания и поведение при сбоях.
5. Проверить UniFFI и Android USB-мост прототипом, затем добавить приложения.
6. Развивать транспорт ESP32 и дополнительные DME независимо от интерфейсов клиентов.

Новые автономные тесты ограничены фризом из [правил Rust](rust-guidelines.md): только основные необходимые проверки или явно запрошенные пользователем сценарии. При выборе таких проверок приоритет имеют корректность пакетов, контрольные суммы и критические сбои обмена. Аппаратные проверки отдельно подтверждают настройки линии, echo, переключение скорости и поведение ECU. Успешные автономные тесты не подтверждают работу записи на реальном блоке.

## Основания и открытые решения

Исходные материалы находятся в `~/git/kek/ms4x`: `README.md`, `MS43.md`, `USB_KLINE.md`, `RUST_ARCHITECTURE.md` и `tools/`. Это локальная исследовательская база, не зависимость сборки. Исследования MS4x Flasher основаны на анализе кода без подключения к ECU.

Открыты выбор UI-стека, конкретные версии зависимостей, формат поставки платформенных пакетов и канал связи с ESP32. Поддержка полноценного Kotlin Multiplatform не входит автоматически в решение использовать Kotlin bindings; её оцениваем отдельно при выборе клиентов.
