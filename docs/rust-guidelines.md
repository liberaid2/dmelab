# Правила разработки на Rust

## Основной принцип

Выбираем самое простое корректное решение. Читаемость и удобство сопровождения важнее потенциального выигрыша производительности. Дополнительную сложность обосновываем конкретным требованием, результатами измерений или существующим вторым применением.

Тайминги K-line, порядок команд, контрольные суммы и целостность прошивки — обязательные требования. Простота реализации не оправдывает нарушение протокола.

## Типы и абстракции

- Предпочитаем конкретные `struct`, `enum` и обычные функции.
- Traits вводим на границах расширения, прежде всего для транспорта и реализаций DME, либо для уже необходимого общего поведения. Не создаём trait для каждого сервиса.
- Generics используем при конкретной пользе. Избегаем длинных списков параметров, сложных `where` и передачи параметров типов через несколько слоёв ради гипотетического переиспользования.
- Состояния соединения, сессии и этапы прошивки описываем через `enum` и явные переходы. Избегаем комбинаций флагов с неочевидным смыслом.
- Typestate с отдельным generic-типом на каждый этап вводим только при доказанной пользе для корректности и читаемости.
- Обычные `Option`, `Result`, `impl Trait` и стандартные `derive` разрешены, когда упрощают код.

## Структура файлов, папок и крейтов

Один модуль отвечает за одну связную задачу. Например, `packet.rs` кодирует и разбирает пакеты, `checksum.rs` вычисляет контрольные суммы, `session.rs` управляет сессией. Если назначение модуля приходится описывать перечислением несвязанных задач, разделяем его по ответственности.

Разделяем состояние, координацию и алгоритмы. `Session` хранит состояние соединения и координирует обмен; парсинг, расчёт контрольных сумм и обработка образа прошивки находятся в отдельных функциях и типах. Не превращаем сессию или другой центральный объект в место для всей логики.

Структуру развиваем постепенно:

- Связанные функции и типы сначала размещаем в одном файле.
- Папку создаём для нескольких модулей с общей предметной ответственностью.
- Отдельный крейт выделяем при самостоятельной ответственности и полезной границе зависимостей, платформы или переиспользования. Размер файла сам по себе не является причиной создавать крейт.

Папки и файлы называем по предметной области: `protocol/`, `diagnostics/`, `flash/`, `faults.rs`. Не создаём сборники `utils/`, `helpers/`, `common/` или универсальные `manager.rs`. Вспомогательный код размещаем рядом с функцией, которой он принадлежит; действительно общий код получает имя, описывающее его назначение.

### Направление зависимостей и видимость

Клиенты используют общий API, реализации DME и необходимые транспорты. Реализации DME и транспортов зависят от контрактов `dmelab-core`. Ядро не зависит от конкретного MS43, CLI, UniFFI или платформенного UI. Платформенные зависимости сосредоточены в соответствующих адаптерах.

Избегаем циклов между модулями. Взаимная зависимость соседних модулей — повод пересмотреть границы или выделить общий контракт с конкретным назначением. Не переносим код в ядро только ради устранения цикла.

По умолчанию элементы приватны. Используем минимально необходимую видимость: `pub(super)`, `pub(crate)` или `pub`. `lib.rs` и `mod.rs` содержат преимущественно объявления модулей, документацию и выборочные экспорты; основную логику размещаем в предметных модулях.

### Размер и развитие модулей

Файл свыше примерно 400 строк рабочего кода или функция свыше 60 строк требуют проверки ответственности и читаемости при ревью. Это ориентиры, а не жёсткие лимиты: связный алгоритм не дробим механически. Тесты, таблицы протокола и генерируемый код оцениваем отдельно от рабочего кода.

Новую функцию добавляем в существующий модуль только тогда, когда она соответствует его назначению. Доступность нужных данных сама по себе не оправдывает такое размещение. Не маскируем god object переносом его методов в несколько файлов без разделения ответственности.

Пример структуры MS43 по мере роста реализации:

```text
dmelab-ms43/src/
  lib.rs
  session.rs
  protocol/
    mod.rs
    packet.rs
    commands.rs
  diagnostics/
    mod.rs
    faults.rs
    live_data.rs
  flash/
    mod.rs
    image.rs
    checksum.rs
    read.rs
    write.rs
```

Создаём эти модули вместе с кодом, без пустой структуры на будущее.

## Владение данными и lifetimes

Долгоживущие объекты обычно владеют своими данными. Начинаем с `Vec<u8>`, `String` и стандартных коллекций. Небольшое копирование допустимо, если избавляет от сложных зависимостей времени жизни. Бесконтрольное копирование больших буферов этим правилом не оправдывается.

Для аргументов функций свободно используем `&str`, `&[u8]` и другие простые заимствования. Полагаемся на автоматическое выведение lifetimes. Явные lifetime допустимы для понятной связи входа и результата; структуры, хранящие ссылки, и сложные lifetime-ограничения требуют обоснования.

`RefCell`, `Cell` и другие механизмы внутренней изменяемости используем при конкретной необходимости. По умолчанию предпочитаем обычный `&mut self`.

## Синхронное выполнение без создания потоков

Библиотека, CLI и будущая Rust-обёртка FFI выполняют операции синхронно в вызывающем потоке. Создавать потоки запрещено: не используем `std::thread::spawn`, `Builder::spawn`, scoped threads, пулы потоков или зависимости, запускающие фоновые исполнители в используемой конфигурации. Tokio и другие async runtimes не подключаем; API проекта не использует `async`/`await`. Выбранный стек описан в [отдельном документе](rust-stack.md).

Сессия имеет одного владельца и выполняет команды последовательно. Не строим внутренние очереди задач и механизмы синхронизации для параллельного выполнения. CLI вызывает библиотеку в основном потоке. Будущее приложение само выбирает поток вызова; Rust-код не переносит работу с UI-потока автоматически.

Прогресс сообщаем синхронными обратными вызовами. Чтения имеют конечные таймауты, отмену проверяем в допустимых точках протокола. При будущем межпоточном вызове со стороны приложения механизм сигнала отмены должен работать независимо от занятой сессии, без создания потока библиотекой.

Запрет относится к выполнению кода продукта. Потоки компилятора и стандартного тестового раннера не меняют эту модель; собственные потоки в тестах не создаём.

## Ошибки и безопасность

Ошибки возвращаем через `Result` с понятными типами и контекстом операции. Не используем `unwrap()` и `expect()` при обработке ответов ECU, файлов и пользовательского ввода. В тестах они допустимы.

Для типизированных ошибок библиотечных крейтов используем `thiserror`. `anyhow` используем только в CLI для объединения ошибок и добавления контекста. Публичный API библиотеки не возвращает `anyhow::Error`; решения о повторах и обработке ошибок принимаем по типам, без разбора текста сообщений.

В ядре `unsafe` запрещён. Если платформенная или FFI-интеграция требует `unsafe`, изолируем минимальный участок за безопасным API, документируем условия безопасности и отдельно проверяем их соблюдение. Выбор библиотеки с внутренним `unsafe` оцениваем отдельно; запрет касается собственного кода ядра.

## Явный и читаемый код

- Используем стандартные макросы и привычные `derive`. Собственные декларативные макросы вводим только для существенного повторения; собственные procedural macros на текущем этапе исключены. Генерация bindings через UniFFI остаётся частью принятой архитектуры.
- Не используем `Deref` для имитации наследования прикладных обёрток. Операции с существенной работой выражаем именованными методами вместо скрытых преобразований.
- Короткие цепочки итераторов допустимы. Для сложных ветвлений, изменяемого состояния и обработки ошибок выбираем цикл или `match`, если они понятнее.
- Следуем стандартному форматированию Rust через `cargo fmt`. Проверки Clippy подключаем вместе с Rust workspace; команды и настройки фиксируем в репозитории.

## Оптимизации

Zero-copy, собственные аллокаторы, пулы буферов и сложные схемы кеширования вводим только после измерений, подтверждающих необходимость. Оптимизация должна сохранять корректность и иметь проверяемый эффект на целевом сценарии. Измерения сами по себе не отменяют запрет на создание потоков и async runtimes.

Обычные простые решения без лишних аллокаций допустимы сразу. Обоснования требуют усложнения кода, а не каждое эффективное выражение.

## Тестирование и ревью

В проекте действует фриз на новые тесты. По умолчанию тесты не пишем. Исключения — самые основные и необходимые проверки корректности и тесты, явно запрошенные пользователем. Не добавляем тесты автоматически для каждой функции, исправления или ради процента покрытия. Для необходимого теста выбираем минимальный сценарий, который проверяет существенное поведение или риск; не расширяем его в матрицу второстепенных вариантов.

Разрешённые тесты проверяют поведение, например корректность пакетов или критический отказ транспорта. Называем их по проверяемому поведению. Не усложняем архитектуру исключительно ради моков. Фриз не отменяет запуск существующих проверок, сборку, форматирование и Clippy.

При ревью сложного решения проверяем, какое требование, измерение или существующее повторное использование его оправдывает. Причину необходимого исключения фиксируем рядом с решением или в описании изменения. Исключение не должно незаметно становиться правилом для остального проекта.

Также проверяем, можно ли понять назначение изменяемого модуля и изменить его поведение без разбора несвязанных частей проекта. При превышении ориентиров размера явно оцениваем необходимость разделения; если сохраняем модуль целиком, кратко объясняем его связность в описании изменения.
