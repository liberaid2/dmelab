# Текущие параметры MS43

Одна верхнеуровневая операция возвращает `LiveData` с показаниями двигателя,
положениями обоих VANOS и командой DISA. Декодирование выполняется в Rust;
CLI и Kotlin работают с именованными полями и единицами в их названиях.
Декодируются все 28 отдельных величин `0B 03`; процентное и коэффициентное
представления лямбда-интеграторов используют одни и те же исходные байты.
Дополнительных запросов или пауз для новых полей нет.

```sh
cargo run -p dmelab-cli -- live
./target/release/dmelab live --port /dev/cu.usbserial-FT1234 --timeout-ms 2000
```

Rust: `Session::read_live_data()`. Kotlin:
`Ms43Client.readLiveData(timeoutMs = 2000u)`. Чтение однократное, без создания
потоков или внутреннего цикла опроса. Порт выбирается по обычным правилам CLI.

## Запросы данных

| Полный пакет с XOR | Ответ используется для |
| --- | --- |
| `12 05 0B 03 1F` | Основных показаний двигателя |
| `12 05 0B 90 8C` | Фактического, целевого и опорного положения обоих валов |
| `12 05 0B 04 18` | Команды управления DISA |
| `12 05 0B 92 8E` | Каналов педали/дросселя и адаптаций, по выбору |
| `12 05 2B 05 39` | Неравномерности и счётчиков пропусков цилиндров, по выбору |

## Выбор блоков

По умолчанию читаются все три. `--blocks` работает и однократно, и с `--watch`:

```sh
./target/release/dmelab live --watch --blocks measurements
./target/release/dmelab live --watch --blocks measurements,vanos
./target/release/dmelab live --blocks digital
./target/release/dmelab live --watch --blocks pedal,rough-running
./target/release/dmelab live --watch --blocks all
```

Доступна любая непустая комбинация пяти блоков. `measurements`, `vanos`,
`digital`, `pedal`, `rough-running` соответствуют `0B 03`, `0B 90`, `0B 04`,
`0B 92`, `2B 05`; псевдонимы CLI — `03`, `90`, `04`, `92`, `2b05`.
`all` выбирает все пять. Порядок всегда measurements → vanos → digital →
pedal → rough-running с пропуском невыбранных блоков. Повтор имени не создаёт повторного запроса. Выбор отдельных полей
внутри блока не сокращает пакет: ECU возвращает блок целиком.

```rust
let selection = dmelab_ms43::LiveDataSelection {
    measurements: true,
    vanos: false,
    digital: false,
    ..dmelab_ms43::LiveDataSelection::default()
};
let data = session.read_live_data_selected(selection)?;
// data.measurements: Some(LiveMeasurements), data.vanos / digital: None.
session.stream_live_data_selected(selection, &should_stop, &mut on_event)?;
```

`LiveDataSelection::default()` сохраняет исходные три блока; новые флаги
`pedal` и `rough_running` выключены. `LiveDataSelection::all()` выбирает пять. `SelectedLiveData` содержит
`measurements: Option<LiveMeasurements>` (все 28 величин),
`vanos: Option<LiveVanos>` (`intake`, `exhaust`) и
`digital: Option<LiveDigital>` (`disa_command_active`),
`pedal: Option<LivePedal>` и `rough_running: Option<LiveRoughRunning>`. В stream событие —
`SelectedLiveDataEvent::Sample(Box<SelectedLiveData>)` либо `Recovering`.
Пустой выбор возвращает `Error::EmptyLiveDataSelection` до идентификации.
Непрочитанные группы не заполняются нулями или прошлым замером. Ошибка любого
выбранного блока отбрасывает весь выбранный набор; stream начинает его заново
с первого выбранного блока. Выбор фиксируется на весь вызов; для смены набора
остановите stream и запустите новый. Остановка и восстановительные паузы прежние.

Однократные FFI-вызовы по-прежнему включают идентификацию; для частого опроса
используйте stream. Даже при одном блоке сохраняется пауза 100 мс между замерами.
Исключение команд сокращает цикл; фактическая частота зависит от ECU и адаптера.
Старые `read_live_data` / `stream_live_data` и плоский `LiveData` сохранены:
они выбирают все три блока и используют общий механизм чтения/восстановления.

## Сессия и тайминги

Свежая Rust-сессия сначала идентифицирует MS43: это ещё четыре запроса,
не входящие в три запроса данных. Повторный вызов на уже идентифицированной
Rust-сессии выполняет только три запроса. Текущая FFI-обёртка создаёт новую
протокольную сессию на каждом однократном вызове, поэтому `readLiveData` каждый раз
включает идентификацию. Непрерывный `streamLiveData` сохраняет одну сессию на всё
время опроса. CLI и FFI работают на 9600 8E1; однократный Rust API сохраняет текущую
согласованную скорость. Чтение скорость не меняет.

Перед каждым запросом данных выдерживается восстановительная пауза 100 мс
из `INITIALISIERUNG` исследованного PRG. Для обмена используется существующий
единый бюджет транзакции: `--timeout-ms` по умолчанию 1000 мс, включая echo и
ответ; пауза в этот бюджет не входит. Это не полное воспроизведение таймеров
EDIABAS: PRG задаёт 2000 мс ожидания ответа и 20 мс продолжения пакета.

## Непрерывный опрос

```sh
./target/release/dmelab live --watch --timeout-ms 2000
./target/release/dmelab live --watch --samples 100 --timeout-ms 2000 > live.log
```

`--watch` использует одну Rust-сессию на 9600 8E1. Идентификация выполняется
один раз после успешного подключения. Каждый следующий замер — три запроса
данных по умолчанию, либо выбранная комбинация `--blocks`. CLI выводит номер,
прошедшее время и выбранные значения в stdout, ошибки
восстановления — в stderr. `--samples` считает только полные успешные замеры;
без ограничения остановка — Ctrl+C. Потоки и обработчик сигналов не создаются.

Rust: `Session::stream_live_data(should_stop, on_event)`. Проверка `should_stop`
производится между замерами, блоками данных и короткими частями восстановительной
паузы. `on_event` получает `LiveDataEvent::Sample(Box<LiveData>)` либо `Recovering` с исходной
типизированной ошибкой и числом последовательных неудач; `ControlFlow::Break(())`
также останавливает цикл. Callbacks выполняются синхронно.
`Box` сохраняет компактность enum после расширения `LiveData`; для получения
самого record по значению в Rust используйте `*data`. Kotlin получает обычный `LiveData`.

В stream-режиме протокол выдерживает минимум 100 мс от завершения предыдущего
обмена до следующего запроса, включая идентификацию, повторные попытки и границу
замеров. Уже прошедшее время учитывается. Режим действует только внутри stream;
порядок команд и тайминги flash не меняются. Повышенная/неопределённая скорость
отклоняется, разгон не выполняется.

Таймаут, ошибка echo, адреса, длины, XOR или отрицательный статус ECU не завершают
сессию. Неудачный замер целиком отбрасывается. После уведомления callback цикл
делает паузу 100, 200, 400, 800 и далее максимум 1000 мс, очищает устаревшие байты
перед новым запросом и начинает полный замер заново. При первоначальном сбое
идентификация повторяется; после успешной идентификации пакетные ошибки не
вызывают её заново. Число последовательных пакетных ошибок не ограничено;
счётчик сбрасывается только после полного успешного замера.

Явная потеря транспорта (`NotConnected`, `BrokenPipe`, EOF и аналогичные ошибки),
отсутствие разрешений, неподдерживаемый ECU и неправильные параметры завершают
вызов ошибкой. Ошибки настройки таймаута и очистки буферов выделяются в
`Error::TransportSetup`: повторяются только `TimedOut`, `WouldBlock` и
`Interrupted`. Прочие ошибки настройки/очистки, включая `Other` после потери
POSIX errno внутри serialport, завершают stream с исходной причиной. Ошибки
самих пакетов по-прежнему восстанавливаются. Молчание ECU без подтверждённого отключения остаётся
восстанавливаемым таймаутом до явной остановки. Старые значения не выдаются как
свежие, неполные выбранные наборы не публикуются.

Для UniFFI используйте `Ms43Client.streamLiveData(timeoutMs, control, listener)`;
контракт остановки и callbacks описан в [Android bindings](android-bindings.md).
Android-приложение должно перейти с собственного цикла `readLiveData` на этот
вызов, чтобы использовать восстановление Rust. Подключение нового API к экранам
приложения не входит в реализацию библиотеки.

## Поля исходных трёх блоков

| Поле | Единицы / смысл |
| --- | --- |
| `engine_speed_rpm` | об/мин |
| `vehicle_speed_kmh` | км/ч |
| `accelerator_pedal_angle_deg` | угол педали, градусы |
| `throttle_angle_deg` | угол дросселя, градусы |
| `mass_airflow_kgh` | кг/ч |
| `intake_air_temperature_c` | °C |
| `coolant_temperature_c` | °C |
| `oil_temperature_c` | °C |
| `radiator_outlet_temperature_c` | °C |
| `ignition_timing_cylinder_1_deg` | угол зажигания цилиндра 1, градусы коленвала |
| `injection_time_bank_1_ms` | мс |
| `idle_speed_integrator_pct` | знаковая интегральная коррекция регулятора ХХ, % |
| `idle_air_control_duty_pct` | ШИМ управления клапаном ХХ, % |
| `intake_camshaft_angle_deg`, `exhaust_camshaft_angle_deg` | фактические углы валов из `0B 03`, градусы коленвала |
| `terminal_15_voltage_v` | напряжение клеммы 15, В |
| `lambda_integrator_bank_1`, `lambda_integrator_bank_2` | коэффициенты коррекции смеси |
| `oxygen_sensor_heater_upstream_bank_1_duty_pct`, `oxygen_sensor_heater_upstream_bank_2_duty_pct` | ШИМ подогревов перед катализатором, оба банка, % |
| `oxygen_sensor_heater_downstream_bank_1_duty_pct`, `oxygen_sensor_heater_downstream_bank_2_duty_pct` | ШИМ подогревов после катализатора, оба банка, % |
| `air_mass_per_stroke_mg` | мг/ход, не нагрузка в процентах |
| `knock_signal_cylinder_2_v`, `knock_signal_cylinder_5_v` | усреднённые сигналы, В; не счётчики детонации |
| `cooling_fan_duty_pct` | управление вентилятором, %, не измеренные обороты |
| `ambient_pressure_hpa` | атмосферное давление `AMP_MES`, гПа; не расчётный MAP |
| `battery_voltage_v` | напряжение питания, В |
| `intake_vanos`, `exhaust_vanos` | `VanosPosition`: `actual_deg`, `target_deg`, `reference_deg` |
| `disa_command_active` | включена ли команда управления DISA |

Коррекции лямбды возвращаются как коэффициенты, а не измеренная λ/AFR.
Процентную коррекцию можно вычислить как `(factor - 1) * 100`.

Положения валов выражены в градусах коленвала в системе отсчёта MS43.
Все три значения каждого вала читаются из одного ответа `0B 90`. Дублирующиеся
фактические положения из `0B 03` доступны отдельно как
`intake_camshaft_angle_deg` и `exhaust_camshaft_angle_deg`. Они не подменяют
`intake_vanos.actual_deg`/`exhaust_vanos.actual_deg`: это позволяет сравнивать
actual и target из одного чтения. Reference — опорное значение, не задание.

Для новых полей применяются типы и коэффициенты `BETRIEBSWTAB`: интегратор ХХ —
big-endian `i16` (`DATA_TYPE 7`) × 0.0015; угол выпускного вала из `0B 03` —
`i8` (`DATA_TYPE 3`) × −0.375 − 60. Типы подтверждены табличным декодером PRG
и `EdiabasNet.OpFix2Flt`. В развёрнутом коде `STATUS_MESSWERTEBLOCK` эти два
значения собираются как беззнаковые; для них следуем явным типам таблицы,
а не копируем это расхождение. Угол выпуска из `0B 90` имеет другой тип (`u8`).
Атмосферное давление — big-endian `u16` по полному смещению 41 × 0.08292;
напряжения по смещениям 25 и 43 × 0.10156; подогревы по смещениям 30–33 × 0.391.
Коэффициенты напряжений взяты из PRG и отличаются от flash-проверки MS4x Flasher.
Подогревы и клапан ХХ отражают команду управления, не температуру и не позицию.

DISA — только флаг команды. Он не подтверждает физическое положение заслонки
и не переводится автоматически в «открыта/закрыта». Исполнительные команды,
поддержание диагностического режима и запуск системных тестов не отправляются.

## Педаль и адаптации: 0B 92

`LivePedal` возвращает все 13 величин блока:

| Поля | Тип исходных байтов / пересчёт |
| --- | --- |
| `idle_adaptation_pct`, `idle_adaptation_in_gear_pct`, `idle_adaptation_ac_pct` | Три big-endian `i16` × 0.001526, % |
| `accelerator_pedal_sensor_1_angle_deg`, `accelerator_pedal_sensor_2_angle_deg` | Два `u16` × 0.0018311, градусы |
| `throttle_sensor_1_angle_deg`, `throttle_sensor_2_angle_deg` | Два `u16` × 0.007294, градусы |
| `throttle_mechanical_stop_sensor_1_voltage_v`, `throttle_mechanical_stop_sensor_2_voltage_v` | Два `u16` × 0.0048828, В |
| `throttle_electrical_stop_sensor_1_voltage_v`, `throttle_electrical_stop_sensor_2_voltage_v` | Два `u16` × 0.0048828, В |
| `throttle_limp_home_sensor_1_voltage_v`, `throttle_limp_home_sensor_2_voltage_v` | Два `u16` × 0.0048828, В |

Все слова big-endian. Два канала педали/дросселя сохраняются отдельно;
адаптированные напряжения упоров не выдаются как текущие напряжения датчиков.

## Неравномерность и пропуски: 2B 05

`LiveRoughRunning` содержит исходный `status: u8` системной проверки и шесть
`CylinderRunning` в порядке номеров цилиндров 1–6. Каждая запись содержит
`cylinder`, знаковый безразмерный `roughness` (`ER_QUO`, big-endian `i16` ×
0.00122) и `misfire_count` (`MIS_SUM_CARB`, big-endian `u16`).
На линии обе группы идут в порядке 1, 5, 3, 6, 2, 4; декодер явно переставляет
их по номеру. Неравномерность не является измерением компрессии, счётчик —
не число пропусков в секунду. Интервал накопления и сброса не установлен.

Автоматический `START_SYSTEMCHECK_LAUFUNRUHE` не отправляется. Исходный статус
сохраняется без обещания актуальности: наличие полного ответа не доказывает,
что проверка выполнялась и значения свежие. Короткий ответ, например только
статус «не запущено», возвращает ошибку длины; stream сообщает `Recovering`
и начинает выбранный набор заново. Нули вместо отсутствующих данных не создаются.
Таймауты, паузы, отмена и восстановление совпадают с другими live-блоками.
В ошибке и событии восстановления сохраняются оба байта запроса:
`command = 0x2B`, `block = 0x05`.

## Полнота и ошибки

Выбранные ответы читаются последовательно, поэтому результат не является атомарным
снимком. Проверяются echo, адрес, XOR, статус `A0` и минимальная полная длина
ответа: 45, 16, 10, 30 и 29 байт для `0B 03`, `0B 90`, `0B 04`, `0B 92`, `2B 05`. Более длинные ответы допускаются,
декодируются известные поля. Числа не ограничиваются искусственными диапазонами.

В однократном API ошибка любого выбранного блока возвращает `Error::LiveDataRead { command, block, source }`,
в Kotlin — `DmeException.LiveDataRead` с `command`, `block` и `details`. Частичный результат
не возвращается, CLI не печатает его. Автоматических повторов, в том числе при
`BUSY`, нет; повтором всей операции управляет вызывающая сторона.

## Основания и проверка

Источник — `~/git/kek/deepobd/analysis/ms43/source/MS430DS0.b1v`, revision 2.00,
и `docs/ms43/` того же репозитория. Использованы `BETRIEBSWTAB`, `BITS`,
`STATUS_MESSWERTEBLOCK`, `STATUS_DIGITAL` и jobs `STATUS_VANOS_NW_LAGE_IST_SOLL_REF_*`.
В `BETRIEBSWTAB` имена `CAM_AV_IN` и `CAM_AV_EX` дублируются для блоков `0B 03`
и `0B 90`. `EdiabasNet.SeekTable` выбирает первое совпадение, поэтому исходные
VANOS jobs получают actual из `0B 03`, а target/reference — отдельными запросами
`0B 90`. Наша библиотека явно использует строки таблицы для `0B 90` и декодирует
все шесть значений из одного ответа. Это осознанная группировка полей, а не
побайтовое воспроизведение последовательности исходных jobs.

Две основные автономные проверки подтверждают точные три запроса, порядок байтов,
масштабы всех 28 показаний `0B 03`, включая знаковые значения, и единый источник
углов `VanosPosition`, а также отказ
при коротком последнем ответе вместо частичного результата. Это необходимое
исключение из фриза на новые тесты. На реальном FTDI/ECU чтение пока не проверялось;
совместимость этого SGBD со всеми вариантами MS43 не подтверждена.

Непрерывный режим добавляет 100 мс между всеми запросами, включая идентификацию.
Однократная идентификация вне stream сохраняет унаследованные тайминги MS4x
Flasher. Влияние этого различия на реальный ECU требует отдельной проверки.

Три необходимые проверки stream подтверждают восстановление после нескольких
таймаутов, повреждённого XOR с оставшимися байтами и короткого ответа, отсутствие
повторной идентификации после успешного подключения, межзапросные паузы,
остановку между блоками, завершение при явном отключении транспорта и при
невременной ошибке очистки буферов после успешного замера.

Также скомпилированы Android Kotlin bindings и собраны `.so` для `arm64-v8a`
и `x86_64`. На macOS выполнен вызов Kotlin → UniFFI → Rust → транспорт Kotlin
с подготовленными ответами: проверены автоматическая идентификация, все поля,
ровно три последующих запроса и типизированная ошибка короткого цифрового блока.

Расширение до всех 28 величин проверено тем же вызовом через Kotlin с отдельными
значениями для каждого нового поля, в том числе отрицательным интегратором ХХ
и знаковым углом выпуска. Повторно пройдены проверки непрерывного опроса;
Kotlin скомпилирован для JVM и Android, `.so` пересобраны для четырёх ABI.
Артефакты этой проверки — `dist/live-measurements-check/`.

Для выбора блоков добавлены только необходимые проверки контракта: все семь
комбинаций отправляют ровно нужные команды, пустой выбор не начинает
идентификацию, а stream одного блока восстанавливается после таймаута и
сохраняет 100 мс между замерами. Прежние проверки полного набора сохранены.
Дополнительно выполнен Kotlin → UniFFI → Rust → транспорт Kotlin: семь
