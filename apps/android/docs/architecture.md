# Архитектура приложений Android и macOS

## Текущая реализация и целевая структура

Подключены четыре модуля [мультиплатформенной архитектуры](multiplatform-architecture.md):
приложения `:androidApp` и `:desktopApp`, библиотеки `:shared` и `:ecu`.
Обе KMP-библиотеки имеют Android и JVM target `desktop`, с `commonMain`,
`androidMain` и `desktopMain`.
`:androidApp` использует каталог `app/`, поэтому расположение APK сохраняется.
macOS-приложение использует Compose Desktop и отдельные desktop bindings UniFFI.
Поставляемая native-библиотека пока только для macOS ARM64; Intel не заявлен.

## Назначение и статус

Приложения dmelab предназначены для работы с ЭБУ BMW, в первую очередь
MS43: подключение, идентификация, диагностика и работа с прошивками. Принятые
ниже решения развивают [архитектуру общего проекта](../../../docs/architecture.md)
и адаптируют стандарт из `~/Downloads/android-doc.md`. Основные правила перенесены
сюда, чтобы разработка не зависела от наличия этого локального файла.

Настроены Compose, Koin Annotations с корневым ComponentScan, Voyager,
Coroutines, DataStore и зависимости USB/JNA. Kotlin API UniFFI и нативные
библиотеки подключены в `:ecu` из `dist/android` и `dist/desktop` общего проекта.
Платформенные генерации изолированы. Инструкция сборки —
[настройка и сборка Android](build.md). Онбординг подключён к обнаружению
FTDI, USB-разрешению и реальной идентификации MS43 через UniFFI. После успеха
открывается `features/hub/`: компактная карточка блока и переходы на четыре
самостоятельных экрана — чтение/запись прошивки, DTC и параметры. Сценарии
используют общий исполнитель операций. На Android работу удерживает foreground
service, на macOS — scope приложения; аппаратная совместимость требует проверки.

Пользовательские сценарии, состояния подключения и правила доступности операций
закреплены в [документе UI и UX](ui-ux.md). При разработке экранов соблюдаем его
вместе с этой архитектурой.

Визуальные значения задаются [токенами дизайна](design-system.md) в
`common/ui/theme/`. Используем фиксированную тёмную тему и стандартные
Material-компоненты; общий слой UI-компонентов не создаём.

## Пакеты и файлы

Зависимости направлены `:androidApp / :desktopApp → :shared → :ecu`;
приложения также подключают `:ecu` для composition root. Обратных зависимостей нет.
`common/` и `features/` — пакеты, а не отдельные Gradle-модули.

```text
app/                              # :androidApp
  src/main/java/dev/coldcat/dmelab/
    MainActivity.kt
    DmeLabApplication.kt
    common/di/AppModule.kt
    common/session/data/          # Android-файлы, журнал, wake lock, запуск сервиса
    common/session/service/
    navigation/NotificationPermission.kt
  src/main/res/                   # manifest-интеграции, launcher, XML-тема
desktopApp/                       # :desktopApp, JVM/macOS
  src/main/kotlin/dev/coldcat/dmelab/
    Main.kt                       # окно, lifecycle и завершение приложения
    DesktopApplication.kt
    common/di/DesktopModule.kt
    common/session/data/          # файлы, журнал, operation host, caffeinate
shared/
  src/commonMain/kotlin/dev/coldcat/dmelab/
    DmeLabApp.kt                   # публичный Compose entry point
    navigation/                   # реализация Router и корневая раскладка
    common/navigation/
    common/platform/              # expect-контракты picker, Back и sharing
    common/resources/             # неизменяемые AppStrings
    common/ui/theme/
    common/session/{domain,data,presentation}/
    features/                     # connection, hub, firmware, diagnostics
  src/commonMain/composeResources/ # строки и иллюстрации экранов
  src/androidMain/kotlin/         # actual системных UI-интеграций
  src/desktopMain/kotlin/         # actual диалогов, Back, экспорта и часов
ecu/
  src/commonMain/kotlin/dev/coldcat/dmelab/common/ecu/
    model/                        # публичные Kotlin-модели, без native DTO
    session/                      # контракты клиента, доступа и stream
    usb/                          # контракт обнаружения адаптеров
  src/androidMain/kotlin/dev/coldcat/dmelab/common/ecu/
    session/                      # клиент, mapping, ошибки, callbacks, остановка
    usb/                          # Android USB Host и FTDI
  src/desktopMain/kotlin/dev/coldcat/dmelab/common/ecu/
    session/                      # native serial-клиент, mapping и stream
    usb/                          # discovery serial-портов за общим контрактом
  consumer-rules.pro              # защита UniFFI/JNA при R8 приложения
```

Внутри сценария используем необходимые терминальные пакеты `data/`, `domain/`,
`presentation/`, `ui/`. Внутри `common/` код также группируется по назначению,
а не складывается в общие `utils/` или `helpers/`.

Feature остаётся в `features/`, даже если пока имеет один экран. В `common/`
попадает инфраструктура или код с подтверждённым использованием несколькими
сценариями. `common` не зависит от feature-реализаций. Общий координатор сессии
обслуживает несколько экранов; внутреннее состояние экрана остаётся в его фиче.

Границы поддерживаем зависимостями Gradle, узкими контрактами, минимальной
видимостью и ревью импортов. Одна фича не обращается к внутренней реализации
другой. Не создаём отдельные Gradle-модули для фич и слоёв, пары `api/impl`
и пустые пакеты под будущие экраны. Целевые четыре модуля разделяют запускаемые
приложения, общий код фич и ECU-интеграцию. Файлы называем по основной сущности
и ответственности.

Генерируемый Kotlin UniFFI подключается отдельными source roots из
`../../dist/android/kotlin` в `androidMain` и `../../dist/desktop/kotlin`
в `desktopMain` модуля `:ecu`. Его пакет `dev.coldcat.dmelab.ffi` задаётся общим
проектом; не переносим и не редактируем эти файлы вручную. Kotlin-адаптеры
размещаем в соответствующих платформенных source sets. Desktop использует
обычный JNA JAR и `.dylib` из `dist/desktop/resources`; Android — JNA AAR и `.so`.
Обе генерации никогда не входят в одну компиляцию. В `:shared` и приложениях
нет импортов FFI, JNA и USB-драйвера. Публичный API возвращает собственные
модели и `EcuException`; нативная причина ошибки сохраняется.

Все экраны, их состояния, Mapper, ViewModel, тема и Router находятся в
`shared/src/commonMain`. Используем Compose Multiplatform resources (`Res`,
`StringResource`) и переносимые lifecycle/ViewModel API. Android `R`, `Context`,
`Intent`, Java IO и системные часы не входят в общий код. Picker, обработчик Back
и отправка файлов имеют узкие `expect`-контракты с `actual` в `androidMain`
и `desktopMain`;
это адаптеры системных действий, а не общие UI-компоненты. Сервис, файловые
адаптеры, разрешения и wake lock сохраняются в Android-приложении.
Desktop-приложение предоставляет свои файловые адаптеры, журнал и управление сном.

## Слои и границы ответственности

```text
Compose → ViewModel → Domain / Repository contract
                              ↑
                    Data implementation → ECU bridge → UniFFI → Rust
                                                                  ↓
                                                  USB / native serial → FTDI
```

Стрелки схемы показывают использование API. На уровне зависимостей Presentation
и Data опираются на Domain; Domain не зависит от Android, Compose, Voyager,
Koin, DTO и генерируемых FFI-типов.

- Rust владеет протоколом MS43, echo, контрольными суммами, согласованием скорости,
  разметкой прошивок, capabilities и допустимыми этапами операций.
- ECU bridge адаптирует FFI-типы и ошибки, выполняет блокирующие вызовы и
  предоставляет Android USB-транспорт либо native serial-клиент desktop.
- Data отвечает за технический доступ к ECU, файлам и настройкам.
- Domain содержит модели и правила сценариев приложения. UseCase создаём для
  самостоятельной операции, а не для переименования вызова Repository.
- Presentation оркестрирует экран, Mapper вычисляет представление, UI отображает.

Не дублируем в Kotlin протокол и ограничения прошивки. Поддерживаемые действия
получаем из capabilities Rust API. Bootloader никогда не стираем и не записываем;
Full Write MS43 изменяет только program и calibration по правилам общего проекта.

## Состояние экрана

```text
Domain / Data → ViewModel → InternalState → Mapper → ScreenState → Compose
                   ↑                                               ↓
                   └──────────────── ScreenEvent ──────────────────┘
ViewModel → ScreenCommand → Container → Router / системный UI
```

У экрана один публичный `StateFlow<ScreenState>` и метод `onEvent(ScreenEvent)`.
ViewModel атомарно обновляет единый InternalState. Stateless Mapper вычисляет весь
неизменяемый ScreenState из актуального снимка; не использует IO, корутины,
Router или Android Context. Форматирование выполняется до UI. Если Mapper нужны
готовые строки, он получает неизменяемые `AppStrings`: composition root один раз
загружает ресурсы на IO dispatcher до создания графа экранов. Чтение и
форматирование строк в Mapper синхронны и не запускают IO.

Container собирает состояние через `collectAsStateWithLifecycle`, получает
ViewModel и обрабатывает команды. Content получает готовое состояние и callback;
не знает о DI, Repository и навигации. Preview не требует production-графа.

ScreenCommand передаёт transient-эффекты: навигацию, snackbar, запуск picker.
Стандарт доставки — buffered Channel с `receiveAsFlow()` и одним активным
потребителем. Команда может ожидать подписчика в живой ViewModel, но Channel
не гарантирует exactly-once при отмене потребителя и не переживает смерть процесса.
Важные подтверждения, результат операции и сведения для восстановления храним
как состояние. Не запускаем запись ECU из transient-команды UI.

## Dependency injection

Используем Koin с Koin Annotations и один Koin-модуль приложения с `@Module`
и `@ComponentScan("dev.coldcat.dmelab")`. Сканируем корневой пакет целиком,
включая `common` и `features`; отдельных Koin-модулей и ComponentScan для фич
не создаём. В Android composition root используется `AppModule`, в desktop —
`DesktopApplication` и `DesktopModule`: в каждом приложении один модуль со своим
набором платформенных реализаций. Koin Compiler Plugin применён ко всем четырём
Gradle-модулям и передаёт metadata аннотированных классов
в корневой ComponentScan. В сгенерированном графе каждой платформы проверяем
ECU-адаптеры, общий исполнитель и ViewModel фич.

Граф запускается в явном composition root приложения, который подключает
единственный Koin-модуль. Не перечисляем вручную каждый аннотированный класс
и не дублируем его регистрацию ручным определением. Внешние объекты, которым
нельзя добавить аннотацию, предоставляем через фабричные определения того же
Koin-модуля.

Зависимости передаём через конструкторы. В Domain, Data, Mapper и UseCase
не используем `KoinComponent`, `get()` или глобальный service locator.
Получение ViewModel через Koin допускается в контейнере экрана.

Scope соответствует владельцу: приложение — общая инфраструктура; ECU-сессия —
координатор, транспорт и исполнитель; экран — ViewModel. Mapper и UseCase
обычно stateless и не требуют scope. Освобождение сессии явно закрывает ресурсы.

## Навигация

Voyager Navigator доступен только адаптеру Router и контейнерам. ViewModel
отправляет семантические ScreenCommand, а не вызывает Navigator напрямую.
Маршруты, аргументы и результаты типизированы. Не передаём в back stack сессии,
USB-объекты, firmware-буферы и DI-зависимости; используем компактные аргументы.

Корневые маршруты — `Connection` и `Hub`; сценарии открываются поверх Hub:
`ReadFlash`, `WriteFlash`, `Dtc`, `LiveData`. Этапы сценария представлены его
ScreenState, а не отдельными записями back stack. Composition root наблюдает
состояние сессии: успешная идентификация заменяет Connection на Hub. При потере
адаптера Hub возвращается к подключению; открытый сценарий сохраняется для
просмотра результата и завершения операции. Его Back ведёт к подключению,
если готовность уже сброшена.

`VoyagerRouter` находится на уровне приложения, где допустимы зависимости от
экранов фич; `common/navigation` содержит типизированные контракты и LocalRouter.
Одна запись одного сценария повторно используется при открытии прогресса.
`rememberViewModelStoreProvider` живёт над Navigator; owner каждой записи имеет
явный ключ Voyager. Покрытие экраном сохраняет ViewModel, удаление записи вызывает
`clearKey`, пересоздание Activity сохраняет хранилище. Общая панель операции
принадлежит корневой раскладке приложения и доступна независимо от текущей фичи.

Сохраняем AndroidX ViewModel как единственный экранный state holder. При
интеграции Voyager явно связываем ViewModelStoreOwner и ключ ViewModel с записью
back stack: пересоздание Activity сохраняет её, удаление экрана освобождает.
Не вводим параллельный ScreenModel для того же состояния.
Системный Back и кнопка экрана направляются в один обработчик события.

## Внешние входы Android

`MainActivity` использует `singleTask` и обрабатывает файловый `ACTION_VIEW`
из `onCreate` и `onNewIntent`. USB attach зарегистрирован с фильтром конкретных
FTDI VID/PID; доверяем повторной инвентаризации UsbManager при ON_RESUME,
а не extras внешнего intent. Подключение не запускает идентификацию автоматически.

Activity-scoped `FirmwareOpenViewModel` готовит входящий файл через `FirmwareFiles`,
сохраняя импорт и отказ как InternalState → Mapper → ScreenState. Он не запускает
операции ЭБУ. Composition root передаёт готовый файл через типизированный Router
на экран записи после идентификации и при свободном исполнителе. Аргументы экрана —
URI копии и режим; исходные байты и Android-объекты в back stack не передаются.

`AndroidFirmwareFiles.importImage` проверяет расширение и фактический размер,
вызывает чистую `validateImage` Rust на IO dispatcher и создаёт отдельную копию
в `cache/firmware_imports/<UUID>/`. Этот узкий путь добавлен в FileProvider.
Внешний временный URI не используется при последующей записи. Старые копии
удаляются при следующем импорте после 24 часов; Android может очистить кеш раньше.
Отмена или ошибка копирования удаляет незавершённую копию. При потере кеша
пользователь повторно открывает исходный файл. Кеш не входит в Android backup.
Проверка формата образа не занимает ECU executor; перед записью остаются
проверки поколения сессии, fingerprint и ограничения Rust.

## Сессия и выполнение операций

Один координатор в `:shared` публикует состояние подключения для всех экранов.
Техническим клиентом и USB/serial-портом владеет `Ms43Access` в `:ecu`:
он переключает выполнение на ECU dispatcher, атомарно отклоняет повторный
вход с Busy и освобождает допуск после закрытия ресурсов. Идентификация
использует тот же владелец порта, что и остальные сценарии.
Блокирующий Rust API выполняется на выделенном последовательном рабочем потоке
приложения. Все обращения к сессии сериализованы; повторный запуск операции во
время занятой сессии возвращает Busy. Rust не создаёт собственные потоки.

Координатор подключения хранит адаптеры, выбор, идентификацию и поколение сессии.
Операция резервирует это поколение и отклоняет конкурирующий запуск без очереди.
Мост открывает порт и Ms43Client на время операции. При непрерывном опросе
Live Data они сохраняются до остановки или терминальной ошибки, а успешные наборы публикуются
по мере чтения. Остальные операции закрывают ресурсы до публикации результата.
Карточка идентификации содержит последний ответ блока, а не состояние
постоянно открытого соединения. При отключении готовность сбрасывается; полученные
данные сохраняются с привязкой к прежней сессии. Подтверждения записи и очистки
DTC привязаны к поколению, поэтому не переживают повторное подключение.

Чтение/запись и диагностические операции принадлежат общему исполнителю, а не
ViewModel. Foreground service удерживает длительную работу и публикует уведомление;
навигация, поворот и закрытие экрана не отменяют обмен. Явный опрос Live Data
использует один `streamLiveDataSelected`; разовое чтение — `readLiveDataSelected`.
Возобновление опроса после других операций не автоматическое.

Domain-модель `LiveDataSelection` содержит три флага: основные измерения,
VANOS и цифровое состояние DISA. `toNative()` в ECU-адаптере преобразует её
в record UniFFI; Domain не зависит от FFI. Принимается любая непустая комбинация.
Исполнитель фиксирует выбор при принятии операции и публикует его в
`ActiveOperation.liveDataSelection`; параметры нельзя менять до завершения.
По умолчанию выбраны все группы. Новые результаты UI содержат только реально
прочитанные группы, без подстановки нулей или старых значений.

На время непрерывного Live Data `AndroidLiveDataWakeLock` удерживает
`PARTIAL_WAKE_LOCK` внутри service-owned Job, независимо от включения CSV.
Он охватывает обмен, восстановительные паузы и финализацию CSV. Освобождение
в `finally` происходит после возврата native-вызова и закрытия файла при остановке,
ошибке или отмене сервиса. Экран не удерживается включённым. Разовое чтение,
просмотр/экспорт логов и другие сценарии этот lock не захватывают.
Используем фиксированный tag и нереференсный lock с арендой 10 минут,
обновляемой каждые 5 минут только в живой корутине операции; обновление
отменяется при выходе. Таймаут ограничивает утечку при зависании, а не время опроса.
В manifest объявлено обычное разрешение `WAKE_LOCK`, без runtime-диалога.

`Ms43LiveDataStream` выполняет блокирующий вызов на выделенном ECU dispatcher.
Rust один раз настраивает порт и идентифицирует блок, затем читает выбранные блоки
на 9600 бод, выдерживает протокольные паузы и восстанавливается после ошибок
пакетов. Android не добавляет задержек или повторов. `onRecovering` обновляет
счётчик последовательных ошибок, сохраняя прежние значения и их время;
`onSample` публикует только новый полный набор и сбрасывает статус восстановления.

Новый `LiveDataStreamControl` создаётся на каждый запуск. Кнопка остановки
вызывает `stop()` с main dispatcher без занятого mutex клиента. Дочерняя корутина
также посылает этот сигнал при отмене сервиса, пока ECU dispatcher занят Rust.
Освобождение control и lease происходит после возврата вызова и закрытия порта.
Остановка проверяется Rust между блоками и во время backoff; текущий транспортный
вызов завершается по своему таймауту.

Синхронный callback выполняет `runBlocking` с Job текущей операции и локальным
event loop, чтобы дождаться записи CSV на IO dispatcher без очереди образцов.
Он не диспетчеризуется на уже занятый ECU executor. Ошибка файла или отмена
сохраняется адаптером, останавливает stream и повторно выбрасывается после его
возврата: UniFFI не превращает её в общую ошибку транспорта.

`AndroidLiveDataLogs` принадлежит общему исполнителю: потоковая запись CSV
выполняется на IO dispatcher, каждый успешный набор выбранных групп сбрасывается
из буфера. На начало файла создаётся `LiveDataCsv` с неизменяемым выбором;
заголовки и accessors определены одной таблицей столбцов. Перед строкой проверяем
соответствие optional-групп выбору. Невыбранные группы не имеют колонок;
набор зафиксирован до закрытия файла. Основная группа включает все 28 величин.
Контракт `LiveDataLogs` предоставляет экрану каталог готовых файлов и экспорт;
ViewModel не владеет писателем. Каталог файлов восстанавливается из CSV.
Незавершённые файлы восстанавливаются без продолжения обмена; отправка использует
FileProvider с узким путём и временным read grant. Подробности —
[формат CSV и восстановление](live-data-csv.md).

Для массового экспорта `AndroidLiveDataLogs` получает снимок готовых файлов,
а `AndroidLiveDataArchives` потоково сжимает их в ZIP на IO dispatcher с отдельной
блокировкой. Сжатие не удерживает блокировку писателя CSV. Незавершённый ZIP
не публикуется; отмена и ошибки закрывают потоки и удаляют временный файл.
Экран использует типизированную цель экспорта CSV/ZIP; контейнер выбирает MIME
и соответствующий системный picker. Архивы хранятся в ограниченном пути кеша
FileProvider; старые файлы очищаются при следующей подготовке.

`LiveDataTiming` хранит длительность разового чтения либо интервал между
успешными наборами stream по монотонным часам и среднюю частоту текущего запуска.
Интервал и частота появляются со второго набора; включают паузы восстановления
и время обработки предыдущего callback. Длительность отдельного замера stream
API не предоставляет. Новый запуск сбрасывает измерения;
Mapper скрывает их при смене идентифицированной сессии так же, как значения.

Для чтения и записи исполнитель измеряет время через общий контракт `monotonicTimeNanos`
и обновляет `ActiveOperation.elapsedMillis` раз в секунду из дочерней корутины
владельца операции. Android actual часов использует `SystemClock.elapsedRealtimeNanos`,
включая deep sleep, desktop actual — `System.nanoTime`. Таймер не зависит от
callbacks прогресса или подписчиков UI и отменяется
при завершении работы. Успешный `FlashResult` содержит итоговую длительность;
Mapper форматирует её до передачи экрану.

SAF-образ читается с пределом 512 КиБ и проверяется Rust до подтверждения.
Подтверждение содержит поколение сессии и SHA-256: непосредственно перед
записью файл читается снова, его содержимое сверяется и повторно проверяется.
При чтении выходной документ открывается до обмена; успех публикуется после
сохранения и закрытия потока. При ошибке приложение пытается удалить документ,
а UI предупреждает о возможном пустом или незавершённом файле.

Перед выполнением сервис синхронно сохраняет технический маркер незавершённой
операции в отдельном журнале SharedPreferences. После смерти процесса он
приводит к сообщению о неизвестном результате, без повторной отправки команды.
Пользовательские настройки и факт запроса уведомлений остаются в DataStore.

Синхронные callbacks прогресса быстро обновляют состояние и не запускают
повторные вызовы сессии. USB read/write имеют конечные таймауты. Прямой
блокирующий API драйвера используем без второго конкурирующего reader.

Отмена корутины не останавливает блокирующий FFI-вызов автоматически. Live Data
использует отдельный stop-control; для flash отмена FFI пока отсутствует.
Не подменяем отмену немедленным закрытием USB. Протокольную
финализацию и освобождение ресурсов завершаем до уничтожения исполнителя.

Для длительных операций владельцем работы служит foreground
service типа `connectedDevice`, с нужными разрешениями и уведомлением.
Уход с экрана и пересоздание Activity не отменяют такую операцию. Service
не гарантирует выживание процесса: после его смерти показываем прерванную
операцию и не возобновляем запись автоматически.

Сервис, wake lock, журнал SharedPreferences и файловые адаптеры находятся
в `:androidApp`. Исполнитель обращается к `OperationHost`, `OperationJournal`,
`LiveDataWakeLock`, `FirmwareFiles` и `LiveDataLogs` из `:shared`.
Сервис получает тот же singleton через узкий `OperationRuntime`;
отдельного исполнителя для сервиса нет. `FirmwareFiles.save` открывает
документ до ECU-обмена, закрывает после сохранения и удаляет незавершённый
документ при ошибке. Формат CSV и правила имён остаются в `:shared`.

## Интеграция macOS

`DesktopOperationHost` запускает тот же `OperationRuntime` в scope приложения.
`DesktopOperationJournal` сохраняет маркер перед обменом на диске; после аварийного
выхода результат считается неизвестным, автоматического повтора нет.
`DesktopLiveDataWakeLock` удерживает `/usr/bin/caffeinate -i` на время непрерывного
опроса, включая CSV и финализацию. Процесс assertion завершается в `finally`
и связан с PID приложения; экран не удерживается включённым.

Закрытие окна или Quit при активной операции показывает диалог. Live Data можно
остановить с ожиданием возврата native и закрытия CSV; для flash требуется дождаться
окончания операции. Принудительное закрытие порта не заменяет остановку.
После завершения освобождаются ViewModel, application scope и ECU executor.

`DesktopUsbAdapterMonitor` сохраняет общий контракт обнаружения, но перечисляет
serial-порты через Rust на IO: при refresh и каждые пять секунд. Для macOS-пары
`cu`/`tty` выбирается представление `cu`; обязательного фильтра VID/PID нет.
Пользователь выбирает путь порта, идентификация остаётся отдельным действием.

`DesktopStorage` использует `~/Library/Application Support/DME Lab/`;
CSV находятся в `live_data_logs/`, временные импорты и архивы — в `cache/`.
Формат CSV, выбор групп, локальное время в имени, суффикс `-n`, partial-восстановление,
переименование и экспорт сохраняют общие правила. Автоматического удаления CSV нет.
Native-диалоги и desktop-экспорт реализованы в `shared/desktopMain`.
Работа с реальным кабелем/ЭБУ и поведение сна требуют отдельной аппаратной проверки.

## Стиль и обработка ошибок

- Official Kotlin style, четыре пробела, минимальная видимость, по умолчанию internal.
- Один production top-level type на файл; вложенные типы контракта допустимы.
- PascalCase для типов и Composable, camelCase для функций и свойств,
  snake_case для Android-ресурсов.
- Именованные аргументы для литералов, null, неоднозначных и однотипных параметров;
  если один аргумент именован, именуем остальные.
- Exhaustive when для sealed/enum без else; семантические состояния вместо
  сочетаний флагов; null обозначает один конкретный случай отсутствия.
- Строки пользователя находятся в ресурсах, оформление использует токены темы.
- Константы и типизированные единицы вместо magic values; комментарии объясняют
  ограничения и причины решений.
- Ожидаемые исходы и ошибки ECU типизированы. Не определяем retry разбором текста.
  Повтор записи автоматически не выполняем.
- CancellationException не поглощаем общим catch; GlobalScope не используем.
  Долгоживущая работа имеет явного владельца и политику завершения.
- VIN, дампы и другие чувствительные данные не включаем в обычные логи.

## Фриз на новые тесты

Новые тесты не пишем и не добавляем, в том числе основные проверки и тесты ради
покрытия. Это явное решение пользователя для приложений, более строгое,
чем исключения родительского руководства. Изменить его может последующее явное
указание пользователя. Требования общего Rust-проекта остаются в его документах.

Фриз не отменяет сборку, Android Lint и запуск существующих проверок.
Настроенного порога покрытия нет. Аппаратные проверки отдельно подтверждают
совместимость кабеля, настройки линии, echo, таймауты и смену скорости;
успешная сборка и автономные проверки не подтверждают работу с реальным ECU.

## Порядок реализации

1. Проверить прототип USB → UniFFI → Rust: разрешение, подключение, идентификация
   MS43, таймауты, смена скорости, отмена и отключение на оборудовании.
2. Реализовать экран подключения и идентификацию с состоянием общей сессии.
3. Добавлять диагностику и чтение по мере готовности Rust API.
4. Подключать запись после проверки ядра на стенде, включая поведение при сбоях.

## Порядок работы агента

До изменения кода агент полностью читает этот документ и применимые инструкции
AGENTS.md. При изменении интеграции также читает документы общего проекта.
При работах по KMP/macOS и модульным границам также читает
[согласованную целевую схему](multiplatform-architecture.md).
Структуру пакетов выбирает по ответственности изменяемого сценария.

Согласованные решения меняются только по явному указанию пользователя. Нельзя
ослаблять правила, отключать проверки или переписывать документацию ради
оправдания реализации. Если задача противоречит решению, агент обозначает
противоречие до реализации; явные указания пользователя имеют приоритет.

Перед завершением агент проверяет изменённый код:

- Сейчас — `:androidApp`, `:desktopApp`, `:shared`, `:ecu`.
  Common не зависит от внутренних реализаций фич,
  Domain не получает платформенные и FFI-зависимости.
- Один Koin-модуль на приложение с корневым ComponentScan; нет дублирования регистраций
  и service locator в прикладной логике.
- Voyager остаётся за Router; UI получает ScreenState и отправляет ScreenEvent;
  Mapper чистый, команды не подменяют сохраняемое состояние.
- ECU-сессия имеет одного владельца; блокирующие вызовы выполняются вне main;
  отмена и освобождение ресурсов соблюдают этапы протокола.
- Нет новых тестов, дублирования протокола в Kotlin и операций записи bootloader.

Нарушения исправляются до завершения. Для изменений кода, ресурсов или сборки
запускаем из `apps/android`:

```sh
./gradlew :androidApp:assembleDebug :androidApp:lintDebug :shared:lint :ecu:lint
```

При изменениях общих библиотек или desktop также компилируем
`:desktopApp:classes`; изменения native-упаковки проверяем через
`:desktopApp:packageDmg` и Android release с R8. Запуск и аппаратный обмен
проверяются отдельно от компиляции и создания пакета.

Дополнительно запускаем существующие проверки, относящиеся к изменению.
Для изменений только документации проверяем содержание, согласованность правил
и локальные ссылки. Итоговый отчёт содержит изменения, фактически выполненные
проверки, ошибки и причины пропуска проверок. Аппаратную проверку не заявляем
без реального выполнения.

Форматирование в Android Studio задаётся `.editorconfig`. Android Lint проверяет
Android-код; специальные автоматические проверки архитектурных импортов пока
не подключены. Эти границы проверяются при ревью. Статический анализ расширяем
по мере появления кода; фриз на новые тесты сохраняется.
