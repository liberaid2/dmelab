# Repository Guidelines

## Обязательные документы

Перед изменением кода прочитайте [README.md](README.md) и документы:

- [Архитектура](docs/architecture.md) — ответственность крейтов, расширение по DME и транспорту.
- [Стек Rust](docs/rust-stack.md) — зависимости, модель выполнения и границы ошибок.
- [Правила Rust](docs/rust-guidelines.md) — стиль, ограничения языка и организация модулей.

Соблюдайте их при реализации и ревью. Не меняйте согласованные решения без явного указания пользователя. Если задача противоречит документации, обозначьте противоречие до реализации; явные указания пользователя имеют приоритет. Обновляйте документацию вместе с изменением согласованного решения. Не ослабляйте правила ради обхода ограничений.

## Назначение и структура

dmelab — Rust-библиотека для диагностики и прошивки DME; первый этап — MS43, FTDI K-line и macOS CLI. Крейты в `crates/`: `dmelab-core`, `dmelab-ms43`, `dmelab-transport-serial`, `dmelab-cli`, `dmelab-ffi`. Документация находится в `docs/`, будущие приложения — в `apps/`. Создавайте каталоги вместе с реализацией. При изменениях FFI и Android-сборки прочитайте [контракт bindings](docs/android-bindings.md); пакет Kotlin — `dev.coldcat.dmelab.ffi`.

Ядро содержит общие контракты и не зависит от конкретных DME, UI или serial API. Исследования в `~/git/kek/ms4x` используйте для соответствующих задач; это локальная база, не зависимость сборки. Отделяйте результаты анализа от подтверждённого поведения оборудования.

## Обязательные ограничения Rust

- Простота и читаемость важнее оптимизаций; тайминги и корректность протокола обязательны.
- Bootloader не стираем и не записываем. Full Write MS43 изменяет только program и calibration по правилам MS4x Flasher; границы описаны в архитектуре.
- API синхронный и блокирующий. Запрещены создание потоков, пулы, фоновые исполнители, Tokio, другие async runtimes и собственные `async` API. Проверяйте конфигурацию зависимостей на скрытые потоки.
- Используйте `serialport` для serial, `thiserror` для ошибок библиотеки, `anyhow` только в CLI, `clap` для команд и `tracing` для логов.
- Собственный `unsafe` в ядре запрещён. Сложные traits, generics, lifetimes и собственные макросы требуют обоснования по правилам Rust.
- Один модуль — одна связная ответственность. Размер свыше примерно 400 строк рабочего кода на файл или 60 на функцию требует ревью структуры, без механического дробления. Избегайте god objects и сборников `utils`.

## Сборка и тестирование

Workspace создан, команды документированы в README. Используйте `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings` и `cargo test --workspace`.

В проекте фриз на новые тесты: по умолчанию их не пишите. Исключения — самые основные и необходимые проверки и тесты, явно запрошенные пользователем. Не добавляйте тесты ради покрытия или каждой новой функции. Подробности — в правилах Rust. Существующие относящиеся к изменению проверки запускайте; автономные тесты не подтверждают аппаратную совместимость. Не заявляйте о проверках, которые не выполнялись.

## Коммиты и запросы на слияние

Используйте короткие сообщения с конкретным действием, например `Добавить проверку пакетов MS43`. В PR опишите цель, изменения, проверки и связанные задачи. Обоснуйте необходимую сложность; объясните пропущенные проверки. Не включайте несвязанные изменения, секреты и локальные настройки.
